## 2026-02-08

### Major Refactor: Modular Activation Component System

**Separated activation types into independent, modular components**
- Modifiers are now their own activation type (separate from zones)
- Drag type is now its own activation type (separate from zones and buttons)
- Screen zones, modifier keys, drag types, mouse buttons, and keyboard shortcuts are all independent
- Each component can be enabled/disabled independently

**New Component Architecture:**
- Created `ActivationComponents.swift` with component configuration system
- `ActivationComponentConfig` protocol for component configurations
- Concrete configs: `ModifierKeyConfig`, `ScreenZoneConfig`, `DragTypeConfig`, `MouseButtonConfig`, `KeyboardShortcutConfig`
- `GestureActivationComponents` struct stores all component configs for a gesture
- Added `components` field to `Gesture` struct (optional during transition for backward compatibility)

**Dynamic UI Generation (Foundation)**
- Added `ActivationComponentUIMetadata` with field specifications
- Extended `ActivationProvider` protocol with `getComponentUIMetadata()` method
- Created `ActivationComponentService` to query plugins for UI metadata
- UI is now modular and extensible (ready for plugin-provided metadata)

**Completely Rewrote GestureConfigurationSheet:**
- Now uses component-based configuration instead of hardcoded activation types
- Each component has a toggle card (with icon, title, description)
- Configuration views show/hide based on which components are enabled
- Clean visual hierarchy with colored cards for each component type
- Preview shows all enabled components in a readable format

**Example Usage Scenarios Now Possible:**
- Zone only (no modifiers): Click in top-right corner triggers action
- Modifiers only (no zone): Hold Cmd+Ctrl anywhere triggers action
- Zone + Modifiers: Hold Cmd+Ctrl and click top-right
- Drag only: Drag with left button (no zone or modifiers required)
- Any combination of the 5 component types

**MouseButtonTrigger Enhancements:**
- Added `.none` and `.any` options to `MouseButton` enum
- `.none` is now the default (no mouse button required)
- `.any` matches any button press
- Updated `DragModifier.from(mouseButton:)` to handle new cases

**Backward Compatibility:**
- All existing gestures continue to work
- Legacy `GestureTrigger` and `ActivationSettings` still present
- Automatic migration from legacy format to components via `GestureActivationComponents(fromLegacyGesture:)`
- Conversion back to legacy format via `toLegacyActivationType()` 
- `updatingComponents()` method creates new gesture from updated components

**Code Organization:**
- New `Detection/ActivationComponents.swift` file (component definitions)
- New `Services/ActivationComponentService.swift` file (component query service)
- Extended `ActivationProvider` protocol in `ActivationCoordinator.swift`
- Completely rewrote `UI/GestureConfigurationSheet.swift` (now component-based)

**Future Work:**
- Detection plugins will provide their own UI metadata via `getComponentUIMetadata()`
- UI will become fully dynamic, building itself from plugin metadata
- Plugins can add new activation types by implementing the protocol
- No more hardcoded activation types in UI code

This refactor makes the activation system truly extensible and modular, setting the foundation for plugin-provided UI components and custom activation types.

### Refactor: Removed Gesture-Awareness from Detection Plugins
- **Problem**: Detection plugins were violating single responsibility by understanding
  gesture structure through `gestureUsesActivation()` method. Plugins had to inspect
  gesture fields (modifiers, dragModifier, activation types) to determine if they
  were needed, creating tight coupling between detection layer and gesture configuration.
- **Solution**: Introduced **ActivationMapper** — a central service that understands
  gesture structure and maps gesture properties to activation types.
- **Changes**:
  * New file: ActivationMapper.swift containing all gesture→activation mapping logic
  * ActivationCoordinator now uses ActivationMapper instead of asking plugins about gestures
  * Removed `gestureUsesActivation()` from ActivationProvider protocol
  * Removed `validateGate()` from ActivationProvider protocol
  * Added `getGateValidationMetadata()` to ActivationProvider protocol
  * Plugins now only provide detection metadata, not gesture interpretation
  * Precision gate validation moved to coordinator using mapper
- **Refactored Plugins**:
  * ModifierKeyDetectorPlugin: Removed gesture inspection, provides modifier state metadata
  * MouseButtonDetectorPlugin: Removed gesture inspection, provides button state metadata
  * ScreenZoneDetectorPlugin: Removed gesture inspection
  * KeyboardShortcutDetectorPlugin: Removed gesture inspection
  * AppConfigurationDetectorPlugin: Removed gesture inspection
- **Benefits**:
  * True separation of concerns: plugins detect, mapper interprets
  * Reduced coupling: plugins don't depend on Gesture structure
  * Better testability: clear boundaries for unit tests
  * Easier maintenance: all gesture interpretation in one place (ActivationMapper)
  * Changes to Gesture fields only affect mapper, not all plugins
- **Note**: Internal plugin optimizations (like checking if drag gestures exist before
  installing monitors) are still fine — that's implementation detail, not architectural
  responsibility violation. The key improvement is that plugins no longer need to
  understand *what makes a gesture use their activation type*.
- **Follow-up Fix**: Discovered and fixed additional gesture structure inspection:
  * GestureLookup was checking `gesture.activationType` — now uses ActivationMapper
  * KeyboardShortcutDetectorPlugin was filtering by `gesture.activationType` — now uses ActivationMapper
  * MouseButtonDetectorPlugin was filtering by `gesture.activationType` — now uses ActivationMapper
  * ActivationMapper is now the **single source of truth** for all gesture→activation mapping
  * ZERO direct `gesture.activationType` checks remain in detection layer
