### Refactor: Removed Gesture-Awareness from Detection Plugins
- **Problem**: Detection plugins were violating single responsibility by understanding
  gesture structure through `gestureUsesActivation()` method. Plugins had to inspect
  gesture fields (modifiers, dragModifier, activation types) to determine if they
  were needed, creating tight coupling between detection layer and gesture configuration.
- **Solution**: Introduced **ActivationMapper** — a central service that understands
  gesture structure and maps gesture properties to activation types.
- **Changes**:
  * New file: ActivationMapper.swift containing all gesture→activation mapping logic
  * ActivationCoordinator now uses ActivationMapper instead of asking plugins about gestures
  * Removed `gestureUsesActivation()` from ActivationProvider protocol
  * Removed `validateGate()` from ActivationProvider protocol
  * Added `getGateValidationMetadata()` to ActivationProvider protocol
  * Plugins now only provide detection metadata, not gesture interpretation
  * Precision gate validation moved to coordinator using mapper
- **Refactored Plugins**:
  * ModifierKeyDetectorPlugin: Removed gesture inspection, provides modifier state metadata
  * MouseButtonDetectorPlugin: Removed gesture inspection, provides button state metadata
  * ScreenZoneDetectorPlugin: Removed gesture inspection
  * KeyboardShortcutDetectorPlugin: Removed gesture inspection
  * AppConfigurationDetectorPlugin: Removed gesture inspection
- **Benefits**:
  * True separation of concerns: plugins detect, mapper interprets
  * Reduced coupling: plugins don't depend on Gesture structure
  * Better testability: clear boundaries for unit tests
  * Easier maintenance: all gesture interpretation in one place (ActivationMapper)
  * Changes to Gesture fields only affect mapper, not all plugins
- **Note**: Internal plugin optimizations (like checking if drag gestures exist before
  installing monitors) are still fine — that's implementation detail, not architectural
  responsibility violation. The key improvement is that plugins no longer need to
  understand *what makes a gesture use their activation type*.
- **Follow-up Fix**: Discovered and fixed additional gesture structure inspection:
  * GestureLookup was checking `gesture.activationType` — now uses ActivationMapper
  * KeyboardShortcutDetectorPlugin was filtering by `gesture.activationType` — now uses ActivationMapper
  * MouseButtonDetectorPlugin was filtering by `gesture.activationType` — now uses ActivationMapper
  * ActivationMapper is now the **single source of truth** for all gesture→activation mapping
  * ZERO direct `gesture.activationType` checks remain in detection layer

### Fix: Cascading Efficiency Chain for Activation Gating
- **Root Cause**: ActivationCoordinator used OR logic across all gates and skipped
  "always-active" types (like mouseButton) during dependency building. This meant
  mouseButton monitors were never gated, and holding a mouse button without modifiers
  could satisfy a screenZone gate independently — enabling screen zone tracking and
  drag monitors unnecessarily, causing ~2% CPU on every mouse drag.
- **Fix**: Replaced flat dependency set with per-gesture efficiency chains. Every
  non-infrastructure type now participates in the chain regardless of efficiency score.
  Evaluation uses AND-within-group (all predecessors in a gesture's chain must be
  satisfied) and OR-across-groups (any gesture's complete chain suffices).
- The most efficient type in each gesture's chain gets an empty gate group (always
  passes), making it unconditionally active for that gesture. Types only used as
  chain intermediates are properly gated by their predecessors.
- Example: gesture "⌘ + Right Drag + Top Left" builds chain
  modifierKey(100) → mouseButton(90) → screenZone(20).
  - modifierKey: unconditional (top of chain)
  - mouseButton: gated by {modifierKey}
  - screenZone: gated by {modifierKey, mouseButton}
  If a separate "Middle Click" gesture exists, mouseButton also gets an
  unconditional group (it's top of that chain), keeping it always active.
- Removed `isAlwaysActive` bypass from evaluation — chain structure now
  determines what runs, not a blanket efficiency threshold.
- **MouseButtonDetectorPlugin**: Added `initializeButtonState()` to detect
  already-held buttons when monitors enable (mirrors ModifierKeyDetector's
  `initializeModifierState`). Handles the case where user holds a mouse button
  before pressing the gating modifier key.

### CPU Optimization: Eliminate Redundant System Queries During Dragging
- **ScreenZoneDetectorPlugin**: Added cached drag/modifier state to eliminate repeated
  OS queries during mouse dragging. Previously, `DragModifier.currentSystem` and
  `NSEvent.ModifierFlags.currentSystem` were called on every mouse event (60+ times/sec
  during drags), causing ~2% CPU overhead. Now queries system state once per mouse event
  and caches for use in zone processing. Cached state cleared on tracking disable.
- **MouseButtonDetectorPlugin**: Improved `validateGate` precision to prevent screen zones
  from activating when held button doesn't match any drag gesture requirement. Adds debug
  logging when gate validation fails to help diagnose activation issues.
- Result: Eliminates CPU spike during mouse dragging when drag gestures are enabled.

### Settings Overhaul — Unified Settings Architecture with Search and Subcategories

**Single SettingsProvider protocol drives all settings**
- `SettingsProvider` protocol: one property `settingsEntries: [SettingsEntry]`.
  Each entry targets a `SettingsCategoryDescriptor` and optional `SettingsSubcategoryDescriptor`.
  Categories and subcategories are auto-created from whatever entries exist.
- `SettingsCategoryRegistry` collects all entries, auto-groups into `ResolvedCategory`
  and `ResolvedSubcategory` structs. Settings tab reads entirely from this.
- Well-known descriptors: `SettingsCategories` enum (general, detection, dataManagement,
  about) and `DetectionSubcategories` enum (general, detection, appearance, performance,
  advanced).

**Unified detection plugin settings into the same system**
- `DetectionPluginSettingsProvider` bridges all detection plugin `PluginSettingDefinition`
  arrays into `SettingsEntry` items. Each definition's `SettingCategory` (.detection,
  .appearance, .performance, etc.) maps to a `SettingsSubcategoryDescriptor`.
- One entry per subcategory group, with a `DetectionSubcategoryView` that renders
  `PluginSettingRow` views with shared `visibilityTrigger` for dependency tracking.
- The old `PluginSettingsView` wrapper is no longer used from settings — the registry
  drives detection settings directly. `PluginSettingRow` and `SliderSettingControl`
  remain in use as the actual rendering components.
- When a category has subcategorized entries, `SettingsView` shows a segmented picker
  to switch between them. This is generalizable to any category, not just detection.

**Settings search**
- Search field in sidebar filters categories and shows a results dropdown.
- Each `SettingsEntry` declares `searchableItems` (title, description, keywords).
  Detection entries auto-generate search items from `PluginSettingDefinition` metadata.

**Reorganized sections**
- Merged "Menu Bar" into "General".
- Renamed "Updates" to "About".
- Sidebar: General → Detection → Data Management → About, plus plugin categories.

**Service plugin settings are dynamic**
- `LaunchAtLoginServicePlugin`, `HapticFeedbackServicePlugin`, and
  `MenuBarVisibilityServicePlugin` conform to `SettingsProvider`.
- Adding/removing a plugin automatically adds/removes its settings.
- Plugins create new categories by targeting a new `SettingsCategoryDescriptor`.

**Files:**
- `UI/Settings/SettingsCategoryProvider.swift` — protocols, descriptors, registry
- `UI/Settings/BuiltInSettingsCategories.swift` — built-in + detection bridge + views
- `UI/Tabs/SettingsView.swift` — registry-driven with subcategory picker

  - Root cause: Race condition in ActivationCoordinator's disabling logic. When modifiers were

  - Issue: Zone highlights could remain visible after modifiers were released if an action like
